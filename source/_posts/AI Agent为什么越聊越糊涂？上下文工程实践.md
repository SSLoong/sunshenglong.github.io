你可能遇到过这种情况：刚开始让 AI 修一个问题，它很快就找到了方向。聊了几十轮，贴过日志、讨论过方案、改过几次需求之后，它却重新建议一个早已被否决的方案，甚至忘了你最初强调的“不要改公开接口”。

看上去，Agent 越忙，反而越糊涂。

这个现象不能简单归因于“模型记性差”。有时关键信息已经被截断；有时信息还在，却埋在大量无关内容里；还有些时候，是交接摘要把“准备测试”写成了“测试完成”。这几种问题，需要不同的处理办法。

这篇文章讨论如何管理 Agent 每一步实际看到的信息，并提供一个可下载的对照实验。资料核验截至 **2026 年 9 月 23 日**；文中的 CSV 案例是虚构教学场景，实验脚本已在本地运行，尚未进行模型能力对比，不包含未经验证的效果数据。

*概念配图：把累积历史整理成可用的工作上下文，保留重要约束，并让原始资料仍然可以找回。*

## 一、先分清：它是没看到，还是没用好？

假设我们让 Agent 修复 CSV 导入的重复记录问题。早期讨论过按 `email` 去重，后来改成 `tenant_id + external_id`，同时要求不新增依赖、不改公开 API。

讨论过程中，又塞进来几百行构建日志、几个完整文件和一些与当前任务无关的页面问题。下一轮，Agent 提议安装新的 CSV 库，并继续按邮箱去重。

至少有四种可能：

| 表现 | 可能的原因 | 首先检查什么 |
| --- | --- | --- |
| 完全不知道新要求 | 截断、摘要或检索遗漏 | 实际发送给模型的输入里有没有这条要求 |
| 重复提出旧方案 | 新旧方案同时存在，状态不清 | 是否明确记录了哪项决定已被替代 |
| 读过正确材料仍然答错 | 干扰、位置效应或任务推理失败 | 保留相同证据，减少干扰后是否仍然失败 |
| 声称做完了未做的事 | 计划、推测与工具观测混在一起 | 有没有对应执行结果，以及结果是否属于当前版本 |

排查时，不能只看聊天界面。界面展示的全部历史，未必就是这一轮真正提交给模型的内容；中间可能经过摘要、裁剪或检索。要定位问题，需要观察最终输入以及它的组装过程。

### 长窗口不等于均匀可靠的读取能力

《Lost in the Middle》在多文档问答和键值检索任务中发现，相关信息的位置会影响模型表现，部分模型在信息位于上下文中间时表现更差。这说明“信息已经放进去”与“模型能稳定利用”是两回事，但论文中的结果不能直接当成所有新模型、所有任务的性能结论。[论文原文](https://arxiv.org/abs/2307.03172)

Chroma 的 Context Rot 报告进一步考察了输入长度、干扰内容等因素，展示了被测模型并不均匀地利用长上下文。它提供了值得复现的现象，而不是一个通用于所有产品的“超过多少 token 就会变笨”的阈值。[研究报告](https://www.trychroma.com/research/context-rot)

因此，本文把“越聊越糊涂”当作一组待诊断的行为。“注意力预算”可以帮助理解取舍，却不是一桶能按 token 精确扣减的资源；也不能只凭注意力计算复杂度，就证明模型必然随聊天长度单调退化。

## 二、上下文工程管理的是每一步的信息供给

提示词决定怎样表达要求；上下文工程还要处理规则、任务进度、工具描述、检索材料和历史消息怎样共同进入模型。Anthropic 将它描述为持续整理模型推理时可用信息的过程。[上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

为了落到工程实现，我会先把信息分成三个地方：

| 位置 | 保存什么 | 更新方式 |
| --- | --- | --- |
| 原始记录 | 用户消息、工具调用、完整日志、文件版本 | 追加记录，保留可追溯性 |
| 任务状态 | 当前目标、有效约束、决定、进度和待解决问题 | 根据新证据显式更新 |
| 本轮工作上下文 | 当前动作所需的规则、状态、证据和近期交互 | 每轮按需组装 |

这个划分是本文的设计建议，不是某个框架的固定接口。

原始记录负责回答“发生过什么”，任务状态负责回答“现在是什么情况”，本轮上下文负责支持“下一步怎么做”。同一条完整日志可以留在磁盘里，本轮只提供错误摘要和可再次读取的位置。

```text
用户请求与修正 ──→ 更新任务状态
工具执行结果 ───→ 保存原始证据
                         │
                  按当前动作选择材料
                         ↓
       有效规则 + 当前状态 + 相关证据 + 近期交互
                         ↓
                    模型决定下一步
                         ↓
               执行、验证、更新状态
```

这里的“外部记忆”需要具体的读写机制。建一个文件或向量库，并不会让 Agent 自动记住里面的内容。什么时候写入、如何检索、如何确认版本，都属于系统的一部分。

## 三、实践：给任务准备一份能接班的状态快照

仍然使用 CSV 导入案例。我会把当前状态写成下面这样，而不是要求下一轮从全部聊天记录里重新推断：

```yaml
goal: 修复 CSV 导入时的重复记录
constraints:
  - 不新增依赖
  - 不修改公开 API
decisions:
  dedup_key: [tenant_id, external_id]
  superseded: 按 email 去重的早期方案已废弃
observed_state:
  file: src/importer.py
  behavior: 当前仍按 email 去重，尚未修改
verification:
  status: not_run
  required_cases:
    - 跨租户同 ID
    - 同租户重复 ID
next_step: 检查现有去重实现和测试，再提出最小修改
```

真正接入项目时，还应记录每项状态的来源，例如用户消息 ID、工具调用 ID、提交版本或文件哈希。上面的简化示例用来展示字段分工，并不代表这些结论已经在某个真实仓库中得到验证。

### 1. 把约束和聊天摘要分开

“不要新增依赖”可能只占八个字，却会影响所有实现选择。它不应该因为出现得早，就在压缩历史时消失。

我的处理方式是，把当前有效约束作为独立字段保存。用户明确修改要求时，更新约束并保留修改来源；不能让旧要求永久生效，也不能把资料中的一句建议当成用户的新决定。

### 2. 区分事实、假设和计划

“怀疑跨租户冲突”是待验证假设；“测试出现跨租户误去重”是观测；“准备补测试”是计划。这三者即使讨论的是同一件事，也不该压成同一个“已完成”条目。

一个实用约定是：状态中的完成标记要能指向证据。修改之后的测试结果才支持这次修改；旧提交上的绿色结果不能自动继承到新版本。

### 3. 给废弃方案留一句原因

彻底删除旧方案，有时会让 Agent 再次花时间探索它。我更倾向于保存一条短记录：

> 按 email 去重的方案已废弃：最终需求要求以租户和外部 ID 共同标识记录。

通常不需要保留围绕这个方案的全部争论，但应该保留足以避免重走弯路的决定和依据。

### 4. 在恢复工作时核对真实环境

快照可能过期。接班后应核对当前分支、文件修改和相关测试，而不是把摘要当成高于现实的事实来源。

Anthropic 的长任务 Harness 实践使用进度文件、功能清单与 Git 历史帮助后续会话恢复工作，并强调逐步推进和验证。值得借鉴的是让进度落在可检查的产物上，而不是依赖一句“之前已经搞定”。[长任务 Harness 实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

## 四、工具输出、检索和压缩怎样配合？

### 工具先返回足够决策的信息

假设测试工具输出了两千行日志，当前动作只是判断应该修哪里。我会让工具优先返回：

```json
{
  "status": "failed",
  "failed_case": "test_same_external_id_across_tenants",
  "observation": "不同租户的记录被错误合并",
  "full_log": "artifacts/test-run-017.log",
  "truncated": true
}
```

这是自拟的接口示例。关键是同时交代结果、依据入口和是否截断；需要深入时再读取完整日志。只返回一句“失败了”，与不加选择地回传全部内容一样，都可能增加下一步的不确定性。

Anthropic 的工具设计文章讨论了返回与任务相关的信息，以及提供精简、详细等响应形式。工具接口的设计会直接改变 Agent 接收到的上下文。[工具设计文章](https://www.anthropic.com/engineering/writing-tools-for-agents)

### 检索需要来源和时效

读到一个文件路径不等于知道文件内容；检索到旧版本接口文档，也不等于可以据此修改当前实现。

我会让证据片段带上来源、版本或读取时间，必要时重新读取。对于用户上传材料、网页和日志中的指令式文字，也要保留来源边界：它们可以是待分析的数据，不能因为进入上下文，就自动升级为系统要求。

检索遗漏同样需要被观察。模型没答对，可能是相关证据从未被选进来，继续调整模型提示词未必能解决问题。

### 压缩保留的是接下来仍有用的状态

压缩前，可以逐项检查这些信息是否还在：目标、有效约束、已确认决定、关键证据入口、未解决问题和下一步。可以先移走重复成功日志、已经完整落盘的长输出，以及与当前任务无关的讨论。

但“压得更短”不应成为单独的验收标准。若摘要把禁止修改接口的约束删掉，即使篇幅减少了九成，也可能让后续行为偏离要求。保留摘要所依据的记录范围，有助于发现遗漏后回查。

预算也需要具体实现：为下一轮输出和可能的工具返回留余量，用目标模型对应的 token 计数方式估算输入；不要把中文字符数直接当成 token 数，也不要假定所有模型都适用同一个占用百分比。

Anthropic 将压缩、结构化笔记和隔离子任务列为长任务的上下文管理手段。它们提供不同的取舍，并不意味着每个任务都需要多 Agent。[相关工程讨论](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

如果只是一个局部问题，一份维护良好的状态快照可能就足够。引入子 Agent 时，也要控制交接内容；把各自的完整历史全部拼回主会话，可能重新制造相同的问题。

## 五、一个可以自己跑的对照实验

为了把“有效整理”和“信息丢失”区分开，我准备了一个只依赖 Python 标准库的[实验材料生成脚本](/downloads/code/context-engineering-demo.py)。它不会联网，也不会调用模型。

下载后运行：

```bash
python3 context-engineering-demo.py --output context-demo
```

输出目录包含三份提示材料和一份人工检查标准。目录必须尚未存在，以免覆盖此前的实验记录。

| 材料 | 内容 | 本地生成字符数 |
| --- | --- | ---: |
| A：完整历史 | 旧建议、最终修正、证据和 120 行无关背景日志 | 7,947 |
| B：状态快照 | 保留任务所需事实、有效约束和来源编号 | 549 |
| C：有损摘要 | 只剩“修复重复导入并补测试” | 365 |

**表中是脚本实际生成的 Unicode 字符计数，不是 token 数、准确率或成本。** B 是手工编写的理想化快照，用于演示信息取舍；它不证明自动摘要器也能保留这些信息。

### 第一步：用 A、B 检查约束遵循

分别在全新、相互独立的会话里提交 A 和 B，使用相同模型版本、参数与输出要求。不要先运行 A，再在同一会话里让模型回答 B，否则前一份材料会污染后一组条件。

检查回答是否满足六项要求：使用最终的联合去重键、不新增依赖、不改公开 API、承认测试尚未运行、覆盖两个指定场景，以及只提出计划、不声称已经完成操作。

A 和 B 保留了完成这个探针所需的信息，但同时改变了长度、组织形式和新旧方案的显著程度。所以它们适合比较两种上下文策略，不能单独证明是哪一个因素带来了变化。

### 第二步：用 C 检查如何面对信息不足

C 故意删除了关键要求。合理表现是指出不知道最终去重键或实现限制，并请求补充，或者给出明确标注条件的方案。

不能要求模型凭空还原已经被删除的约束，再把做不到归咎于“记忆不好”。这一组考察的是面对信息不足时是否会猜测，不应与 A、B 使用完全相同的评分标准。

### 第三步：一次改变一个因素

脚本支持改变背景日志数量，以及关键事实在背景材料中的位置：

```bash
python3 context-engineering-demo.py --output case-start --fact-position start
python3 context-engineering-demo.py --output case-end --fact-position end
python3 context-engineering-demo.py --output case-long --noise-lines 600
```

前两个命令的关键事实相同，只移动材料位置；第三个保持默认位置，增加背景量。这里调节的是事实块相对背景日志的位置，固定的任务说明和输出要求仍然保留。

这只是一个小型决策探针。要评价完整 Agent，还需要真实仓库、工具执行和结果验收。可以先为每种条件重复若干次，再扩展任务样本，记录模型版本、实际 token 用量、耗时、错误类型和是否正确请求补充信息。

本篇完成的是材料生成与本地校验，没有运行这些模型对比。因此这里没有“压缩后准确率提升多少”的结论。即使之后观察到差异，也需要区分这个合成案例的结果与真实任务的效果。

评测 Agent 时，应检查最终产物和环境变化，而不只看它的自述。Anthropic 的评测指南也区分了任务轨迹、评分方式与最终结果，这对避免“说完成就算完成”很有帮助。[Agent 评测指南](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 六、日常使用时，可以先改变三个习惯

**修改需求时，说清楚替代关系。** 比起只说“改成联合去重”，更完整的表达是：“之前按邮箱去重的方案废弃；改为租户和外部 ID 联合去重；其他约束继续有效。”

**长任务切换阶段时，更新任务状态。** 从排查进入实现、从实现进入验证，分别确认当前目标、已知事实和待办。让 Agent 列出仍未完成的验收项，通常比不断追加“继续”更容易发现偏差。

**新开会话前，准备交接包。** 至少保留目标、约束、改动位置、证据入口、未解决问题和下一步，并在新会话核对实际文件。清空历史可以移除干扰，也可能连必要信息一起丢掉。

我希望上下文工程最终带来的变化，是让 Agent 的工作更容易被接续和检查：当前执行的是哪个版本的要求，结论来自哪里，哪些只是计划，遇到遗漏时应该去哪里找回证据。

这些问题一旦有了明确答案，长对话就不再只是越堆越高的消息列表，而能逐步变成一个有状态、有依据的工作过程。
