你在给团队选 AI 编码工具，打开 SWE-bench、Aider 排行榜，看到某个模型或 Agent 分数高出 5 个百分点，准备下单。等等——这个分数测的是什么？在什么环境下测的？失败案例是哪些类型？换到你的代码库和工作流，这 5 个点还剩多少？

评测榜是**条件证据**，不是采购说明书。技术负责人在读榜时，必须先问清楚四件事：**测的是模型能力还是 Agent 能力？在什么 harness 下测的？默认权限和审批模式是什么？成本和超时设置如何？** 不问清楚就下结论，容易把"在特定编辑格式下的模型表现"误读成"通用 Agent 全能力"，或者把"默认审批更严格"误读成"根本不能自主执行"。

这篇文章会拆解主流 Coding Agent 评测榜的机制，给出读榜的 checklist，帮技术负责人把榜单当工具而非教条。

**核心结论先行**：
1. SWE-bench Verified 曾是业界标杆，但 OpenAI 在 2026 年 2 月指出污染与测试质量问题后不再报这个榜；7 月再对 SWE-bench Pro 审计，发现约 30% 任务有破坏性问题，收回"采用 Pro"的推荐。
2. Aider Polyglot 测的是"在 Aider 编辑工作流里、按指定 edit format 改代码"的能力，不是通用 Agent；换 harness 或 edit format 会显著改变分数。
3. Terminal-Bench 同时报 MODEL 和 AGENT 两列，正好说明"模型能力"和"Agent 脚手架"是两回事。
4. 读榜时要警惕：是否同 harness、是否污染、是否饱和、是否覆盖你的语言与仓库形态、是否把默认审批误读成能力边界。
5. 落地建议：用自家代表性任务做影子评测，要求供应商披露 harness 与工具集，不要为 1–2 个点的榜差轻易换栈。

## 一、评测榜在测什么：四层拆解

在讨论具体榜单之前，先把"分数"拆开看。一个 Coding Agent 的表现由四层因素共同决定，混在一起看容易得出错误结论。

### 1.1 第一层：模型能力

这是基础：在相同的 Agent harness 和工具集下，换不同的模型（如 GPT-4 → Claude Sonnet → Gemini），**只有模型的推理、代码生成、规划能力在变**。

SWE-bench 官方的 **Bash Only** 对比视图就是这个用法：所有模型都用同一个 mini-SWE-agent 环境，只换模型 backbone。这样得出的分数差异，才是"模型本身"的差异。

### 1.2 第二层：Agent / harness 能力

Agent harness 是模型外面的脚手架，包括：
- **工具集**（能调用哪些工具：搜索、编辑、运行测试、浏览器）
- **工具循环设计**（单轮 vs 多轮迭代、失败重试、自我修正）
- **上下文管理**（检索策略、动态加载、窗口压缩）
- **编辑格式**（whole-file rewrite vs diff-based vs search-replace）

Terminal-Bench 榜单同时报 **MODEL** 和 **AGENT** 两列分数，就是为了分开看：
- MODEL 列：纯模型能力（在标准 harness 下）
- AGENT 列：模型 + 完整 Agent 脚手架

如果只看 AGENT 列的总分，你不知道高分是模型强还是脚手架好；只看 MODEL 列，你不知道这个 Agent 的工具和迭代设计能给模型加多少分。**两列一起看，才能判断"换模型"和"换 Agent"各自的收益。**

### 1.3 第三层：默认权限与审批模式

这一层最容易被误读。一个 Agent 能否"自主执行终端命令、自己跑测试、自己修 bug"，**不是能力问题，而是产品默认配置问题**。

举例：
- Agent A 默认设置是"每次命令都要人工审批"
- Agent B 默认设置是"自动批准所有命令"

如果你在评测环境里给 A 开启自动批准权限，它也能"自主执行"；如果你给 B 关掉自动批准，它也会"逐步等人确认"。**这不是 Agent 能不能做，而是产品方为了安全性和可控性，默认给了什么权限。**

读榜时常见的误区：
- ❌ 错误："Agent A 在榜单上分数低，因为它不能自主跑测试"
- ✅ 正确："Agent A 在默认配置下需要更多人工审批，评测方可能按其默认设置测试，也可能统一配置为自动批准；具体要看评测报告的配置说明"

**不要把"默认审批更严"写成"根本不能自主执行"。**

### 1.4 第四层：成本与超时

评测通常会设置：
- **超时限制**（如单任务最多 10 分钟、最多 50 次工具调用）
- **成本上限**（如单任务最多消耗 $5 的 API 费用）

不同的成本和超时设置，会直接影响分数：
- 如果允许更长时间和更多 token，Agent 能多轮试错，分数会更高
- 如果限制很紧，复杂任务可能来不及完成就被中断

读榜时要看清楚：这个榜的"pass@1"是一次机会还是允许多次尝试？有没有看到测试失败反馈后重试的机会？成本和时间预算是多少？

**四层小结**：模型是基础，harness 是放大器，权限是安全阀，成本是约束条件。看榜单分数时，要问清楚每一层的配置，才能判断这个分数对你的场景有多少参考价值。

## 二、主流榜怎么读

### 2.1 SWE-bench 家族：标杆地位与争议

**SWE-bench** 是目前最知名的 Coding Agent 评测基准，官方地址：https://www.swebench.com/

**核心设计**：
- 从 12 个流行的 Python 开源仓库（如 Django、Flask、matplotlib）中抽取真实 GitHub issue
- 每个 issue 附带：问题描述、修复前的代码、修复后的 gold patch、自动化测试
- Agent 的任务是读问题描述，生成 patch，通过测试
- 指标：**% Resolved**（通过测试的任务占比）

**版本演进**：
- **Full**：约 2294 个 instances
- **Verified**：500 个人工筛选的高质量子集，曾是业界标杆
- **Lite**：更小的快速验证集
- **Multilingual / Multimodal**：扩展到其他语言和多模态任务
- **Pro**：由 Scale AI 维护的加强版（更新到 V2 等版本）

**Bash Only 对比视图**：
SWE-bench 官网提供的一个关键视图，所有模型都用同一个 **mini-SWE-agent** 环境，只换模型 backbone。这是"同 harness 比模型"的标准做法，能排除 Agent 脚手架的干扰。

**争议与时间线教训**：

#### 2026-02-23：OpenAI 不再报 Verified

OpenAI 发布文章《Why we no longer evaluate SWE-bench Verified》（https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/），指出：

1. **污染问题**：多个厂商的模型能复现 gold patch 的细节（如变量命名、注释风格），怀疑训练时见过题
2. **测试质量问题**：审计"模型常失败"的 27.6% 子集，发现其中至少 **59.4%** 存在有缺陷的测试：
   - 测试过于严格（正确解也被拒）
   - 测试过于宽松（错误解也能通过）
   - 测试覆盖不足
3. **结论**：Verified 对 frontier 模型已不够用，建议改用 **SWE-bench Pro**

#### 2026-07-08：收回 Pro 推荐

OpenAI 再发文章《Separating signal from noise in coding evaluations》（https://openai.com/index/separating-signal-from-noise-coding-evaluations/），对 SWE-bench Pro 的 731 个公开任务进行审计：

- 自动化标出约 **27.4%** broken
- 人工标注约 **34.1%** 有问题
- 估计约 **30%** 任务有破坏性问题

**问题类型**：
- 过于严格的测试
- 欠指定的 prompt（任务描述不清）
- 低覆盖的测试（无法验证修复是否正确）
- 误导性的 prompt

**OpenAI 的最终立场**：收回此前"采用 SWE-bench Pro"的推荐，提醒开发者仔细审视结果。

**重要澄清**：OpenAI 收回推荐 ≠ 数据集消失。Scale AI 仍在维护 SWE-bench Pro（包括 V2 等版本），官方仓库：https://github.com/scaleapi/SWE-bench_Pro-os 。其他团队和研究者仍可使用，但技术负责人在读榜时应该知道：**这个榜曾被业界领先方审计后认为有显著质量问题。**

**读 SWE-bench 的要点**：
1. **看清版本**：是 Verified、Pro、Full 还是 Lite？不同版本的难度和质量差异很大
2. **看清对比条件**：是 Bash Only（同 harness）还是各家自己的 Agent？
3. **警惕污染**：如果多个模型都能复现 gold patch 细节，可能训练时见过题
4. **不要盲信绝对值**：30% 的任务可能有破坏性问题，分数差距可能来自"谁更擅长绕过坏测试"而非"谁更会修 bug"

### 2.2 Aider Polyglot：编辑格式耦合的榜

**Aider** 是一个流行的 AI 编码工具，官方排行榜：https://aider.chat/docs/leaderboards/

**Polyglot 测什么**：
- 225 道较难的 **Exercism** 编程题，跨 C++/Go/Java/JavaScript/Python/Rust 六种语言
- 模型需要按指定的 **edit format**（如 whole-file、diff、search-replace）修改代码，并通过单元测试
- 通常给**两次尝试机会**：第一次失败后可以看到测试反馈，再改一次

**关键细节**：
- 榜单注明 **last updated November 20, 2025**（引用时请以官网最新日期为准）
- 官方表上会列出模型名称、分数（如 gpt-5 high 88.0%）、测试日期、cost（如 $0.45）
- **换 edit format 会显著改变分数**：同一个模型，用 whole-file rewrite 和用 diff-based edit，分数可能差 10–20 个百分点

**Aider Polyglot 不是什么**：
- ❌ 不是"通用 Coding Agent 全能榜"
- ❌ 不是"在任意 IDE 或工作流下的表现"
- ✅ 是"在 Aider 的编辑工作流里、按特定 edit format、解决中等难度编程题"的能力

**读 Aider 榜的要点**：
1. **edit format 很重要**：如果你的工具用的编辑格式和 Aider 不同，这个榜的参考价值有限
2. **Exercism 题型窄**：都是算法/数据结构题，不涉及"大型仓库里找 bug"或"跨文件重构"
3. **两次机会**：如果你的工作流只给一次机会，要看 pass@1 而非 pass@2
4. **成本要看**：官方表上列出了每个模型的 cost，便宜 5% 但慢 20% 的模型，在你的场景里不一定更优

**Aider 的价值**：它提供了**多语言**覆盖和**编辑格式对比**，这是 SWE-bench（只有 Python）没有的。但不要把"Aider 榜第一"等同于"任何场景下最强"。

### 2.3 Terminal-Bench：MODEL vs AGENT 的对照组

**Terminal-Bench** 专注于终端环境里的长程任务，官网：https://www.tbench.ai/

**核心设计**：
- Agent 需要在终端里完成复杂任务（如调试、配置、多步骤部署）
- 榜单同时报两列分数：
  - **MODEL**：在标准 harness 下，纯模型能力
  - **AGENT**：模型 + 完整 Agent 脚手架（工具、循环、上下文管理）

**为什么这个设计重要**：
- 你能直接看到"换模型"和"换 Agent"各自的增益
- 如果一个 Agent 的 MODEL 分数高但 AGENT 分数低，说明它的脚手架没有充分发挥模型能力
- 如果 AGENT 分数比 MODEL 分数高很多，说明它的工具和迭代设计很强

**版本演进**：
- 站点当前展示 **Terminal-Bench 4.0**，版本在持续迭代
- 引用具体百分比前，请打开官网核对当日数字（页面可能加载不全或更新）

**读 Terminal-Bench 的要点**：
1. **看两列**：不要只看 AGENT 总分，要对比 MODEL 和 AGENT 的差距
2. **任务类型**：终端任务偏运维、调试、配置，和"纯写代码"的场景不同
3. **长程能力**：这个榜测的是多步骤任务，对工具循环和错误恢复能力要求更高

## 三、读榜 Checklist：技术负责人必问的 8 个问题

在看任何 Coding Agent 评测榜之前，先问清楚这 8 个问题：

### 3.1 是否同 harness？

**核心问题**：榜上的模型/Agent 是用同一套工具和脚手架测的，还是各家用自己的 Agent？

- ✅ **同 harness**（如 SWE-bench Bash Only）：分数差异主要来自模型能力，可比性强
- ❌ **异 harness**：分数差异可能来自工具集、循环设计、权限配置，可比性弱

### 3.2 是否公开轨迹？

**核心问题**：能否看到 Agent 的完整执行轨迹（调用了哪些工具、中间结果、失败模式）？

- ✅ **公开轨迹**：你能判断失败是模型问题还是工具/权限问题
- ❌ **只有分数**：你不知道为什么失败，无法判断换到你的场景会如何

### 3.3 是否污染风险？

**核心问题**：训练数据是否可能包含评测题？

- **SWE-bench Verified**：OpenAI 2026-02 文章指出多个模型能复现 gold patch 细节，怀疑污染
- **Exercism / LeetCode**：公开题库，污染风险高
- **私有数据集**：如果评测方自己造题且不公开，污染风险低

**警惕信号**：如果多个厂商的模型在同一个榜上都突然大幅提升，且能复现标准答案的细节，可能训练时见过题。

### 3.4 是否饱和？

**核心问题**：榜上的头部模型是否已经接近或达到满分？

- 如果头部模型已经 95%+，这个榜对区分顶级模型已经没用（ceiling effect）
- 如果榜还有区分度（头部在 60–80%），说明任务还有难度

**HumanEval 的教训**：早期 Python 编程题榜单，头部模型已经饱和，学术界已经不太用它区分模型。

### 3.5 是否覆盖你的语言与仓库形态？

**核心问题**：评测的任务类型、语言、仓库规模，和你的实际场景有多接近？

- **SWE-bench**：只有 Python，12 个开源仓库
- **Aider Polyglot**：C++/Go/Java/JS/Python/Rust，但都是 Exercism 算法题
- **Terminal-Bench**：终端任务，偏运维和调试

**你需要问**：
- 我的团队主要用什么语言？（如果是 C# 或 Scala，上述榜单都不直接覆盖）
- 我的仓库是大型单体还是微服务？（SWE-bench 的仓库规模偏小）
- 我的任务是写新功能还是修 bug？（不同任务对模型的要求不同）

### 3.6 是否把"默认审批"误读成能力？

**核心问题**：榜单描述是否清楚区分"Agent 不能做"vs"默认设置下不自动做"？

**常见误读**：
- ❌ "Agent A 不能自主跑测试" → 实际上是默认需要人工审批
- ❌ "Agent B 能自己修 bug" → 实际上所有 Agent 都能，只是 B 的默认权限更宽松

**正确读法**：
- 看评测报告的配置说明：是否统一配置为自动批准？还是按各家默认设置测试？
- 如果按默认设置测试，分数差异可能来自"谁的默认权限更宽松"，而非"谁的能力更强"

### 3.7 成本和超时如何设置？

**核心问题**：单任务的时间和成本预算是多少？允许几次尝试？

- **成本**：如果允许 $10/任务，模型可以多轮试错；如果限制 $1，可能来不及完成
- **超时**：如果限制 5 分钟，复杂任务可能被中断；如果允许 30 分钟，Agent 有更多时间探索
- **尝试次数**：pass@1（一次机会）vs pass@2（看到错误后重试）差异很大

**你需要问**：这个榜的成本和时间设置，和我的实际预算接近吗？

### 3.8 是否有统计显著性说明？

**核心问题**：分数差距有没有显著性检验？还是只是随机波动？

- 如果榜单只报单次运行结果，1–2 个百分点的差距可能没有统计意义
- 如果榜单报了置信区间或多次运行的方差，可以判断差距是否显著

**建议**：不要为 1–2 个点的榜差轻易换栈，除非这个差距经过显著性检验。

## 四、落地建议：从榜单到选型

### 4.1 用自家任务做影子评测

榜单是别人的场景，不是你的场景。最可靠的做法是：

1. **挑选代表性任务**：从你的积压 issue 或历史 PR 里挑 10–20 个有代表性的任务
2. **统一配置**：给候选 Agent 设置相同的权限、工具集、超时和成本预算
3. **对比结果**：不只看通过率，还要看：
   - 失败模式是什么？（理解错需求 vs 工具用不好 vs 权限不够）
   - 成本分布如何？（某些 Agent 可能通过率高但成本高 3 倍）
   - 轨迹质量如何？（某些 Agent 可能瞎试，某些有清晰规划）

### 4.2 要求供应商披露细节

在选型或采购时，向供应商要求披露：

- **Harness 与工具集**：用的是什么脚手架？有哪些工具？
- **权限配置**：默认哪些操作需要审批？能否配置？
- **成本模型**：单任务平均成本是多少？有没有成本上限保护？
- **失败模式**：哪些类型的任务容易失败？为什么？
- **轨迹可见性**：能否导出完整执行轨迹供审计？

### 4.3 不要为小分差轻易换栈

**场景**：Agent A 在某个榜上 65%，Agent B 在同一个榜上 67%，你准备从 A 换到 B。

**等等**：
- 这 2 个点的差距有统计显著性吗？
- 换栈的成本是多少？（迁移、培训、适配）
- B 的失败模式在你的场景里是否更少？
- B 的成本和 A 接近吗？

**建议**：除非分数差距大于 5 个百分点且经过显著性检验，或者你在影子评测中验证了 B 确实在你的场景里更好，否则不要轻易换栈。

### 4.4 持续跟踪，但不追逐每个新榜

评测榜在快速迭代，每个月都有新的榜单出现。技术负责人应该：

- **关注机制变化**：如果某个榜改了评测方式（如 SWE-bench 从 Verified 到 Pro），了解为什么改
- **关注头部争议**：如果业界领先方（如 OpenAI）公开质疑某个榜，关注他们的论据
- **不追逐每个新榜**：除非新榜覆盖了你之前未评估的维度（如新语言、新任务类型），否则不需要每次都重新选型

### 4.5 建立内部基线

最终目标是建立**你自己的评测基线**：

- 用你的代码库、你的任务类型、你的质量标准
- 定期（如季度）重新评估候选 Agent
- 记录成本、通过率、失败模式的变化趋势
- 当新模型或新 Agent 出现时，先在你的基线上测，再决定是否切换

## 五、总结

Coding Agent 评测榜是条件证据，不是采购说明书。技术负责人在读榜时，必须先问清楚：

1. **测的是什么**：模型能力、Agent harness、权限配置，还是三者混合？
2. **在什么条件下测的**：同 harness、同预算、同超时，还是各家自己的配置？
3. **分数差有没有意义**：是否污染、是否饱和、是否有统计显著性？
4. **和你的场景有多远**：语言、仓库形态、任务类型是否匹配？

**时间线教训**：
- SWE-bench Verified 曾是标杆，2026-02 OpenAI 指出污染与测试质量问题后不再报
- SWE-bench Pro 曾被推荐，2026-07 OpenAI 审计后发现约 30% 任务有破坏性问题，收回推荐
- 榜单质量在演进，技术负责人要跟踪头部争议，而非盲信分数

**落地建议**：
- 用自家任务做影子评测
- 要求供应商披露 harness、工具集、权限配置
- 不要为 1–2 个点的榜差轻易换栈
- 建立内部基线，持续跟踪但不追逐每个新榜

最后，记住一句话：**榜单告诉你"在某个条件下谁更强"，但只有你自己的评测能告诉你"在你的场景下该选谁"。**
